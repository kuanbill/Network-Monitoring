# Docker 與網站獨立告警設計

## 目的與範圍

讓使用者知道是 Docker 系統服務出狀況、網站無法正常回應，還是主機／Agent 失聯。Docker 和網站各自有異常事件及恢復通知；同一台主機的其中一項尚未恢復，不會阻止另一項寄信。

| 主機 | Docker 檢查 | 網站檢查 |
| --- | --- | --- |
| `192.168.6.23` | 既有 Linux Agent：`docker.service` | `https://urc.landagent.com.tw/` |
| `192.168.6.44` | 既有 Linux Agent：`docker.service` | `https://ai.tailan.com.tw/` |

第一版只做觀測和通知。不列舉容器、不檢查 Docker API、不存取 Docker socket、不新增 Agent 的權限、不自動重啟或透過管理端執行遠端命令。Docker 的 `active` 代表 systemd 回報該服務運行，不表示 Docker API、所有容器或網站正常；網站異常也不表示 Docker 是故障原因。

## 設定與量測

- 管理端為這兩台主機各提供獨立的 Docker、網站啟用旗標；新增及既有未設定主機預設關閉。不接受其他 IP 啟用這兩個固定檢查。旗標以既有主機設定 API 保存，更新時省略則保留，不要求重新輸入 Agent Token。旗標出現在公開設定與不含機密的匯出中。第一版不新增設定頁操作元件，提供維護啟停步驟。既有主機的普通編輯不會清掉新旗標。
- Docker 使用 Agent `--services` 回報的 `docker.service`，保留現有 `ssh` 檢查。啟用 Docker 獨立監控須同時啟用 Agent；若要停用 Agent，須先或在同一請求停用 Docker 監控，不接受半啟用設定。上線前確認兩台確實使用系統層級的 `docker.service`；如果是 rootless 或不同服務名稱，先回報差異，不改權限、不假設使用同一個單元。正常 Agent 回報 `active` 為成功；有明確非運行狀態，按原狀態回報；正常 Agent 未回報或回報 `unknown` 則為「無法確認 Docker 服務狀態」，可觸發 Docker 告警但不聲稱已停止。若整個 Agent 暫時不可用，Docker 標為無資料，交由既有主機／Agent 告警，Docker 本輪不視為失敗或恢復。
- 網站獨立使用管理端所在位置的網路與 DNS，而非直接連線到 `.23` 或 `.44`。成功須收到 HTTP `2xx`；其餘狀態碼（含重新導向）、DNS、連線、憑證驗證及逾時皆有可區分的結果。不跟隨重新導向、不讀取頁面內容、不送 Agent Token 或任何登入資訊。名稱驗證與 TLS SNI 使用指定網域，採系統信任庫，不關閉驗證。此檢查確認網站入口回應，不保證登入後功能正常，也不提供主機本機可達的證據。
- 網站網址由固定 IP 與網址對應表決定，不開放任意網址、通訊埠或跳轉位置，不變更既有 HTTP 檢查只用主機 IP 的限制。每次解析只使用全球可路由單播 IP；混合結果會略過受限位址，若無合法地址則回報 DNS 異常。連線直接使用驗證過的 IP，不重新解析、不使用代理；地址驗證和 TLS 網域驗證缺一不可。在剩餘期限內，未收到 HTTP 回應可試下一個合格位址；第一個完成的 HTTP 回應就是本輪結果，不因非 `2xx` 而找其他位址。若現場 DNS 只提供非公開地址，先確認需求，不為了上線放寬限制。
- 每次網站檢查自 DNS 開始至收到 HTTP 標頭共用單一 5 秒期限。每個固定網站最多一個進行中的探測，不共用會被另一站阻塞的工作名額，不允許無界排隊或新增工作。已開始的檢查逾時算本輪異常；若前一輪探測仍卡住，未能開始的本輪顯示「無資料／前次檢查未結束」，歸零該站連續計數但不開啟或清除事件，也不把主機總覽判為新的異常。逾時後沒有晚到結果可以覆蓋量測狀態。

## 事件、郵件與相容性

- 一輪量測可分別更新三個事件：既有主機、Docker、網站。以主機 ID 加檢查種類識別，不以全台主機共用一組計數。沿用已設定的異常／恢復輪數（預設各 2 次）、通知開關、收件者、寄件工作和有界重試。恢復信仍受現有恢復通知開關控制。
- 例如 `.23` 的 Docker 先故障、網站後故障，兩項各達門檻就各寄一次；即使 Docker 未恢復，網站連續成功也可單獨寄恢復信。同一項只有在確認恢復後才開始下一個事件。Docker 因 Agent 失聯而缺資料時，歸零連續異常／成功計數，不改變已確認事件是否開啟；重新收到有效量測後才再次計數。
- 同一失敗不另外重複寄一封泛用主機信：獨立監控啟用後，網站與對應 `docker.service` 結果不納入既有主機郵件事件的判定與內容。原本的 Ping／TCP／主機 IP HTTP、Agent、本機其他服務仍照舊。若 Agent 失聯而網站也掛掉，主機與網站各有自己的事件；不額外假報 Docker 停止。關閉 Docker 獨立監控但 Agent 仍列出 `docker.service` 時，該項回歸既有 Agent 服務彙整。
- 主機總覽仍可顯示可達主機的任一監測項目異常；沒有本機可達證據仍是 `down`，不因網站回應改成可達。使用現有主機詳情與服務結果區呈現 Docker／網站，不新增頁面；未設定功能的主機維持原有行為。郵件仍以繁體中文指出主機、檢查項目、觀測結果、時間與建議，不寄 Token、SMTP 密碼、原始例外或 URL 查詢內容。網站信僅可列固定的合法網域。
- 事件維持記憶體狀態。重新啟動或變更 Gmail 設定後重新累積；刪除主機、停用檢查或變更相關連線設定會取消相應事件的待送信及重試。已通過有效性檢查並進入一次 SMTP 寄送流程的嘗試（含連線或驗證）不強制中止，但不得再重試作廢的事件。
- 切換 Docker 獨立監控會改變原主機告警的判定範圍，因此重設主機與 Docker 事件，取消兩者的舊待送信，再按新範圍重新量測；不把舊事件改寫為恢復。若原本已寄出的主機異常仍存在，例如 SSH 也故障，重新達門檻時可再寄一封符合新範圍的主機信。網站事件不受這次切換影響；其他設定變更也不清除不受影響的獨立事件。

## 驗收及部署界線

- 隔離測試涵蓋：Docker 與網站交錯故障和分別恢復、Agent 失聯不誤報 Docker、原有主機告警不重複、不因網站回應將主機視為可達、關閉通知／恢復信、改設定或移除主機後的事件失效、設定重載／既有表單保存相容性。
- 使用替身或本機受控測試覆蓋網站 HTTPS 行為、無跳轉、DNS 地址限制、期限與卡住的解析；一般測試不連正式網址、不寄真實郵件、不使用正式設定。
- 程式完成後，正式上線另行確認。先以唯讀方式確認兩台 systemd 單元及實際管理部署對兩個固定網址的 DNS／HTTPS 狀態；如常態回應並非 `2xx`，先確認應監控的入口，不以強制接受重新導向掩蓋。之後才調整既有 Agent 服務參數、短暫重啟 Agent、重建對應管理端及啟用旗標。不刻意關閉正式 Docker 或網站來驗證；必要時可先關閉新增旗標並還原 Agent 服務參數。不要同時啟動兩套管理端共用設定或爭用 `8080`。

具體欄位名稱、內部函式、工作池實作與測試替身由實作者決定；不變更既有管理介面、Agent 及 SMTP 的部署安全界線。
